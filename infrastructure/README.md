# reLIVE AWS setup

Run these JavaScript scripts from your Mac or a lab IDE with Node.js 22 or newer. They use the AWS SDK default credential chain, including your selected AWS_PROFILE. No credentials belong in this folder.

```bash
cd infrastructure
npm install
npm run check
npm run db:migrate
```

If your credentials are under the learnerlab named profile, first run `export AWS_PROFILE=learnerlab`. If your working CLI uses the default profile, keep that configuration. Both scripts verify account 615663614353 and use us-east-1.

`check` only reads AWS resources. It verifies the existing web and images buckets and reports whether relive-listings exists. It does not alter S3 policies or upload files.

`setup:database` creates relive-listings with String PK/SK, SellerIndex (sellerPK/sellerSK), StatusIndex (statusPK/statusSK), on-demand capacity, a NEW_AND_OLD_IMAGES stream and point-in-time recovery. These AWS resources can consume lab credit. Re-running reuses a matching table without deleting records. A mismatched schema stops the script for review. If PITR permission is denied, the table may already have been created; fix the permission issue and rerun, rather than deleting it.

Suggested listing record:

```json
{
  "PK": "LISTING#demo-001",
  "SK": "DETAILS",
  "sellerId": "demo-user",
  "title": "Used textbook",
  "price": 2500,
  "status": "ACTIVE",
  "createdAt": "2026-10-09T06:00:00Z",
  "sellerPK": "USER#demo-user",
  "sellerSK": "2026-10-09T06:00:00Z#demo-001",
  "statusPK": "STATUS#ACTIVE",
  "statusSK": "2026-10-09T06:00:00Z#demo-001"
}
```

The record above is a design example, not inserted by setup. Prices are integer sen. PK spreads distinct listings across partition-key values; SK distinguishes the details item and allows related records later. SellerIndex supports seller queries and StatusIndex supports browsing by status and time. A single popular status can become a hot key at larger scale; this is a small coursework design, not a production scaling guarantee. Index queries require pagination and may be eventually consistent. Changes to status must update statusPK too.

Capture the terminal summary, table keys, both indexes, capacity mode, stream settings and PITR settings for the report. PITR enabled is not proof of successful restoration: recovery testing is a separate later step. A stream enabled is not a Lambda consumer: that integration also comes later.

This setup does not migrate SQLite, create users, deploy Lambda/API Gateway, or change the React app. Existing S3 buckets are reused; there is no need to create duplicate buckets. Next implement and verify DynamoDB CRUD before connecting the application backend.

## Demonstrate CRUD from JavaScript

Run each step separately and capture the terminal and DynamoDB Explore items results:

```bash
npm run demo:create
npm run demo:read
npm run demo:query
npm run demo:update
npm run demo:read
npm run demo:delete
```

These commands target only LISTING#coursework-demo-001 / DETAILS for writes. Create refuses to overwrite an existing item. Update and delete require a matching demo marker and seller. The initial price is 2500 sen (RM25); update sets it to 2000 sen (RM20). Delete is a real deletion of this disposable record, followed by a strongly consistent read verifying absence. Capture before/after screenshots before moving to the next command. Query demonstrates a primary-key Query and both GSIs with pagination. StatusIndex can return other active listings too; it does not alter them. GSI changes may take a short time to appear.

These scripts use your AWS credentials directly and are development tools, not public API handlers. They do not test browser authentication or replace the required website/API CRUD demonstration. Database stream records are generated by writes, but no Lambda trigger has been deployed yet.

## Versioned migrations

Use `npm run db:status` to inspect pending/applied migrations (read only), and `npm run db:migrate` to apply them. This supersedes both legacy table scripts; those scripts now call the same runner and apply ALL pending migrations.

The runner verifies the AWS account, bootstraps the on-demand `relive-migrations` table, and takes a conditional lock before changing application tables. Migration 001 creates or adopts listings; 002 creates or adopts users. Adoption verifies keys, attribute types, index projections and capacity. Missing streams/PITR are enabled and readiness is checked before recording completion. No application records are deleted or copied. SQLite import is a separate future data migration.

History stores migration IDs, source-file SHA-256 checksums and completion timestamps. Never edit or rename an applied migration. Add the next numbered file; current migration files are declarative table specifications, not arbitrary data-transform scripts. Custom index alterations/data backfills require extending the migration execution contract and tests explicitly. The generic runner/helper is shared code and should be reviewed carefully when changed. Applied migrations are skipped; status is history inspection, not live schema-drift auditing.

On failure the migration remains pending; resources already created remain intact. After fixing the error, rerun: operations inspect existing resources before creating anything. These are forward-only operations, with no destructive rollback. The caller needs Describe/Create/UpdateTable, Describe/UpdateContinuousBackups, and GetItem/PutItem/DeleteItem/Query/TransactWriteItems on the migration history table. The application's Lambda role does not need migration-history access.

The lock has no automatic expiry or TTL. This prevents a second process overtaking a slow run. After a crash or expired credentials it may remain. Run `npm run db:status` to see its owner and timestamp. Confirm the original process is stopped (including on teammates' computers), refresh credentials if necessary, then release only that owner:

```bash
npm run db:unlock -- EXACT_OWNER_FROM_STATUS --confirm-stopped
npm run db:migrate
```

Do not force-unlock a running migration. A migration completion transaction also checks lock ownership. Infrastructure control-plane changes and history writes cannot be a single DynamoDB transaction, so restartability is required even with locking.

Run `npm test` in infrastructure for migration-runner tests. They mock AWS responses and do not verify Learner Lab permissions or actual cloud provisioning.
